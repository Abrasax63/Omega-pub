## 1. Objectif et périmètre

Ce plan vérifie que les tâches synthétiques sont déterminées (T1) ou sous-déterminées (T3) conformément à leurs données publiques, que les oracles recalculent les résultats indépendamment du générateur, et qu'aucune information privée n'est exposée.

Il ne mesure pas la performance de ChatGPT, d'Omega fixe ou d'Omega adaptatif. Il ne teste pas les résultats mathématiques L+1/L+2.

## 2. Environnement de référence

- Python 3.12.
- Bibliothèque standard uniquement pour les tests actuels (`unittest`, `json`, `hashlib`).
- Répertoire : `EXPERIMENTS/generators/`.
- Commande de référence depuis la racine du dépôt :

```bash
python -m unittest discover -s EXPERIMENTS/generators -p 'test_*.py' -v
```

Cette commande est déjà celle du workflow GitHub Actions `.github/workflows/t1-t3-generators.yml`.

### Point de conception à traiter

Le code actuel génère le prompt et les paramètres dans la même fonction, mais il n'existe pas encore de validateur dédié qui prouve leur correspondance après sérialisation. La solution recommandée est de créer deux fonctions de rendu déterministes, une pour T1 et une pour T3, puis de vérifier :

```python
assert render_t1(public_parameters) == prompt
assert render_t3(public_parameters) == prompt
```

Ces fonctions de rendu ne doivent lire aucun champ privé. Les tests de mutation doivent démontrer que toute divergence est rejetée.

## 5. Contrôles négatifs obligatoires

Le plan est considéré incomplet tant que les mutations suivantes ne sont pas rejetées :

1. Modifier un coefficient dans le prompt seulement.
2. Modifier un coefficient dans les paramètres publics seulement.
3. Injecter la graine dans le paquet public.
4. Injecter une réponse attendue ou un témoin T3 dans le paquet public.
5. Remplacer les deux témoins T3 par deux valeurs de (b) distinctes mais donnant une même sortie (si une future famille de transformations rend cela possible).
6. Falsifier une sortie témoin sans modifier le paramètre (b).
7. Supprimer une étape ou réordonner les étapes T1 dans le prompt.

Un contrôle négatif réussi signifie que le validateur rejette l'instance mutée ; il ne suffit pas que le test produise une erreur non interprétée.

## 6. Procédure d'exécution future

1. Ajouter les fonctions de rendu canoniques et les tests complémentaires.
2. Lancer la commande de référence localement ou via CI.
3. Archiver la sortie complète, le commit SHA, la version Python et la commande.
4. Vérifier que chaque test négatif échoue pour la raison attendue.
5. Faire une revue indépendante du contrat, des fonctions de rendu et des oracles.
6. Seulement après validation, geler un lot pilote avec manifestes public/privé séparés et empreintes SHA-256.

## 7. Règles de verdict

- **PASS logiciel :** tous les tests existants et complémentaires passent, et les contrôles négatifs rejettent les mutations prévues.
- **FAIL logiciel :** au moins un invariant ou contrôle négatif échoue.
- **INDÉTERMINÉ :** test non exécuté, environnement indisponible, ou résultat incomplet.
- **Non évalué :** comparaison des systèmes A/B/C ; aucun score de performance ne peut être attribué par ce plan.

Ne pas assimiler PASS logiciel à une validation du benchmark ou à une preuve d'avantage Omega.
