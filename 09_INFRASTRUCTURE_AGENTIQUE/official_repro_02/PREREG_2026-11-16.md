# OMEGA-BUGSINPY-OFFICIAL-REPRO-02 — préenregistrement (2026-11-16)

## Pourquoi une nouvelle expérience après #120 ?
La PR #120 a exécuté le module `test.test_utils` sur les commits buggy et fixed de youtube-dl-1 : **79/79 tests PASS dans les deux versions**. Le gate de reproduction a échoué honnêtement (`REPRODUCER_UNCONFIRMED`). Il ne faut pas réinterpréter cette expérience ni remplacer son résultat.

**Nouvel enseignement vérifiable AVANT cette expérience :** le script BugsInPy épinglé [`projects/youtube-dl/bugs/1/run_test.sh`](https://github.com/soarsmu/BugsInPy/blob/11c5f1eea954a42132cfd06bf257766a7963e0fd/projects/youtube-dl/bugs/1/run_test.sh) exige exactement `python -m unittest -q test.test_utils.TestUtil.test_match_str`. La procédure [bugsinpy-checkout](https://github.com/soarsmu/BugsInPy/blob/master/framework/bin/bugsinpy-checkout) **transplante les tests de la révision fixed sur le checkout buggy**, sans y substituer le code de production corrigé. La commande et le transplant constituent donc le changement de protocole, décidé explicitement et gelé ici. **Aucun code du correctif fonctionnel n'est consulté lors du gel des classements.**

Cette étude est une **réparation du reproducteur** sur un cas déjà exploré, donc **PAS** un nouvel holdout aveugle ou une évaluation indépendante de généralisation. Son résultat peut vérifier que le mécanisme de traceback est utilisable en pratique.

## Classements immuables
- **A** : même classificateur lexical de #119/#120, utilisant les appels/noms/imports AST du test transplanté.
- **B** : même score lexical + les frames du traceback réel du **buggy**, selon le boost / tri préenregistrés de #120. Aucun nouveau paramètre, aucune modification de parseur, même inventaire cible.
- Top-10 primaire, top-5 et top-20 secondaires. B paie un test supplémentaire et reçoit davantage d'information que A : comparaison **NON à budget d'information égal**.
- Geler et hacher l'intégralité du classement A/B et les logs du buggy AVANT de télécharger la version fixed de production dans le job oracle. Ne pas accorder une victoire à un outil si aucun traceback exploitable n'est produit.

## Gate et oracle post-gel
1. Exiger `buggy FAIL`, au moins un test lancé, et traceback du paquet `youtube_dl/` mappé à un intervalle AST. Sinon `REPRODUCER_UNCONFIRMED`; A et B ne sont pas comparés scientifiquement.
2. Dans un second job, vérifier le SHA des choix scellés. Récupérer alors seulement le code fixed, tester avec la **même** copie du test fixed, et exiger `fixed PASS`. À défaut `REPRODUCER_UNCONFIRMED`.
3. L'oracle identifie les fonctions modifiées par le diff historique de production, en détectant les hunks non attribuables; si un hunk est ambigu, `ORACLE_PARTIAL_NO_COMPARATIVE_CLAIM`.
4. Le `hit@10` de A et B ne peut être interprété que si reproduction différentielle et oracle complet, et comme **observation locale unique** (pas généralisation).
5. Une trace peut mentionner des fonctions exécutées, pas la cause : les résultats ne sont pas des preuves de réparation ni de diagnostic causal.
6. Aucune suite de réparation/Qwen, aucune API payante ; aucune modification de `main`, CORE ou des PR précédentes; PR brouillon non fusionnée.

## Arrêts et anti-fuite
- Si le test fixed transplanté ne s'installe pas correctement : `TEST_TRANSPLANT_FAILED`.
- Si les 2 versions passent/échouent identiquement : `REPRODUCER_UNCONFIRMED`.
- Si des erreurs de parsing, import manquant, données absentes, durée dépassée, absence de traceback cible : `INDETERMINATE`.
- Ne pas inventer de succès de CI, de correction d'Omega ni d'autonomie avant les runs et artefacts vérifiables.
