# OMEGA-MECHANISM-LOC-01 — préenregistrement du 16 novembre 2026

## But et état initial
Vérifier si un petit **pilote de localisation de mécanismes suspects**, fondé sur les appels visibles dans les tests publics, classe mieux les fonctions susceptibles de contenir le correctif qu'un ordre déterministe de référence. C'est un test de **localisation statique**, PAS de réparation, d'intelligence générale ni de succès d'un agent autonome.

Ce protocole est enregistré **avant inspection du code de la version fixed, de son diff et de toute sortie de localisation**. Ne pas adapter les coefficients de classement après résultat. Il succède à #104 / #115 / #117 / #118 sans changer leurs conclusions. Dans #118, la génération de 40 candidates sur Scrapy-1 n'a pas touché le fichier du correctif. Pour éviter un test a posteriori, **nouveau cas** : [BugsInPy](https://github.com/soarsmu/BugsInPy) `httpie-1`, projet [jakubroztocil/httpie](https://github.com/jakubroztocil/httpie), **commit buggy** `001bda19450ad85c91345eea3cfa3991e1d492ba`, **commit fixed tenu à l'écart** `5300b0b490b8db48fac30b5e32164be93dc574b7`. Métadonnées BugsInPy `soarsmu/BugsInPy@11c5f1eea954a42132cfd06bf257766a7963e0fd`, `projects/httpie/bugs/1/bug.info`; Python 3.7.3 ; tests publiquement déclarés `tests/test_downloads.py`.

**Aucun diff fixed consulté à ce stade.** Les identifiants fixed sont publics : la séparation est *opérationnelle*, non une garantie contre une connaissance préalable du modèle / du développeur.

## Périmètre et budget (avant test)
- Installer **zéro dépendance d'exécution**, aucun appel de modèle, aucune API payante. Parcourir les fichiers Python `httpie/**/*.py` du checkout BUGGY historique (ordre lexicographique) et analyser leur AST, jamais les importer ni les exécuter.
- Inventaire : fonctions libres (`ast.FunctionDef`, `ast.AsyncFunctionDef`) de premier niveau et méthodes directement dans classes de premier niveau (`ClassDef`); décorateurs autorisés pour le classement mais jamais évalués. Fonctions imbriquées et classes imbriquées HORS PÉRIMÈTRE. Les cibles du comparateur sont **exactement les mêmes**.
- Analyser le fichier historique BUGGY `tests/test_downloads.py` et collecter uniquement les noms AST des appels (`Name`, `Attribute.attr`), les classes de tests, les imports et les noms des fonctions de test. Aucune utilisation des lignes corrigées, labels BugsInPy, issues, tests réservés ni trace de correctif pour classer.
- A : **référence déterministe** = fonctions de premier niveau d'abord, puis méthodes, puis tri `(chemin, ligne, qualname)`, sans regarder les appels de test.
- B : score figé d'après les seuls signaux du test :
  - +5 si nom de fonction égal à un nom d'appel dans le test,
  - +3 si nom de classe égal à un nom de classe instanciée ou mentionnée dans le test,
  - +2 si nom du module est cité parmi les noms importés du test,
  - +1 pour chaque jeton commun (maximum 3) entre `qualname` décomposé sur `_/-` et les noms d'appels de test,
  - +1 si nom de module et nom du fichier de test partagent le jeton `download` (cas lexical explicite mais non issu du diff ; applicable tel quel au nouveau cas),
  - pas d'autres bonus ; score nul admis.
  Tri `(-score, chemin, ligne, qualname)`. Les deux bras ont le même inventaire et un budget maximum d'inspection d'**au plus 10 fonctions** pour `hit@10` (aussi `hit@5`, `hit@20` transparents comme analyses secondaires). Identité de chaque cible et rangs A/B archivés.
- Figer le manifeste JSON (commit buggy, inventaire, scores, rangs, SHA-256) **AVANT** de télécharger la version fixed. Un résultat `NO_TEST_SOURCE`, `NO_FUNCTIONS`, `SOURCE_PARSE_ERROR` invalide la comparaison et reste publié.

## Oracle séparé (seulement après gel)
Second job CI, conditionné au premier, télécharge le manifeste scellé et **ensuite seulement** récupère la version fixed exacte. Comparer les sources `httpie/**/*.py` buggy vs fixed par différences de lignes et identifier les fonctions dont les lignes sources historiques modifiées appartiennent à leur intervalle AST. Extraire l'oracle de la SOURCE FIXED (pas des scores). Vérifier les empreintes du manifeste et l'identité des commits.
- Si le correctif est hors du paquet `httpie/`, hors fonction analysable, dans un fichier ajouté/supprimé ou avec une position ambiguë : statut `ORACLE_OUT_OF_SCOPE` ou `ORACLE_AMBIGUOUS`. Ne pas attribuer une réussite fictive.
- Pour les fonctions localisables : métriques primaires `hit@10` de A et B (au moins une cible historique modifiée dans les 10 premières), `min_rank`, `hit@5`, `hit@20`. Déclarer `GAIN_LOCAL_UNIQUE_CASE` uniquement si B hit@10 et non A ; symétrique `REGRESSION`; sinon `NO_DIFFERENCE`. **Un seul cas ne démontre pas un gain statistique.**

## Mécanismes et limites
Le pilote identifie des fonctions dont les signatures / liens lexicaux sont proches des appels de test ; il NE déduit pas le mécanisme causal exact ni ne génère de patch. Un classement amélioré n'établit pas la validité d'un correctif. Le mécanisme précis reste `INDETERMINATE` sans reproduction du test échouant, et l'exactitude de réparation est `NOT_TESTED`.
- Les tests d'intégration historiques sous Python 3.7.3 ne seront pas réputés exécutés. Une étude supplémentaire devra reproduire `buggy FAIL / fixed PASS` avant d'attribuer une amélioration de réparation.
- Vérifier sur des fixtures synthétiques : aucun accès à fixed en phase A, inventaires identiques, scores figés, SHA non altérables, états d'échec exacts, fonction modifiée à rang connu.
- PR brouillon isolée empilée sur #118 ; ne modifier ni `main`, ni CORE, ni les autres PR ; aucune fusion ni promotion automatique. Sans API payante. Les coûts éventuels sont les minutes GitHub Actions.

## Décision falsifiable
Quel que soit le résultat, ne pas changer la formule ni sélectionner un autre cas pour remplacer celui-ci. Si l'expérience est négative, recommander un nouveau protocole utilisant des **traces d'échec réelles** pour améliorer la localisation, plutôt que de recycler les mêmes candidats sur le cas connu.
