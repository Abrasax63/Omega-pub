# OMEGA-OPENMODE-VALIDITY-01 — préenregistrement (2026-11-16)

## Question et antécédents
Ce projet NE prétend PAS découvrir pour la première fois l'idée des vérificateurs. Omega a déjà comparé vérificateurs, décodages contraints et règles fixes, notamment les PR #31, #75, #104, #115 et #117. La question spécifique est ici : **un contrôle statique minimal des modes d'ouverture des fichiers retire-t-il sans perte connue les corrections d'AST qui déclencheraient un `ValueError` certain, à règles et budget de génération constants ?**

**Attention : étude rétrospective, pas test en aveugle indépendant.** Les modes binaires incompatibles ont été observés dans l'artefact public #117 avant ce protocole. Ne pas appeler cela un gain de généralisation ou d'intelligence.

## Deux bras à comparer
- A (référence) : **40** candidates sans filtre, chacune marquée seulement "AST parseable" tant que l'appel n'a pas été testé.
- B (même entrée/budget de génération) : application unique d'un **filtre statique avant exécution**, fondé sur l'appel `open` directement modifié, et sur une **chaîne littérale Python** pour le mode d'ouverture. Rejeter seulement lorsqu'une candidature introduit/maintient explicitement `encoding=...` dans un appel `open` dont le mode littéral contient `b`. Pour les modes non littéraux, noms rebindés et cas ambigus : statut `UNKNOWN`, **pas "valide"** ; ne jamais forcer une déclaration de sûreté.
- Le moteur ne reçoit ni tests réservés ni patch corrigé pendant le filtrage. Signaler séparation `REJECT_CERTAIN_BINARY_ENCODING`, `NOT_REJECTED_STATIC`, `UNKNOWN`, `SOURCE_MISMATCH`.
- Les deux bras conservent les mêmes 40 IDs/sha de source. Budget d'examen commun = une classification et au plus un micro-test par ID (40 unités théoriques pour chaque bras) ; mesurer le nombre effectif d'appels `open` et CPU sans présenter les durées GitHub comme coût LLM égal. Ne jamais donner un score de réparation à un test syntaxique.

## Tests non-régression pré-déclarés
1. `open(...,'rb',encoding='utf-8')` et `open(...,'wb',encoding='latin-1')` doivent échouer avec `ValueError` ; les appels sans encodage doivent rester utilisables, et les ouvertures en mode texte + encoding doivent réussir.
2. Modes `r`, `w`, `a` et mode par défaut explicite correctement reconnus ; modes binaires `rb+`, `ab`, `xb` rejetés si `encoding` explicite. Aucun rejet binaire sur un nom de variable `mode` dont la valeur est inconnue.
3. Recalcul et correspondance SHA-256 de chaque patch avec le checkout buggy, validation AST du fichier complet, absence de modification des fichiers source ; tout décalage de hash du manifeste entraîne arrêt.
4. Si un candidat est rejeté, vérifier dans un micro-test isolé que Python lève effectivement `ValueError` sur ce mode/encodage. Un résultat qui n'est pas `ValueError` est une fausse alarme et doit être publié.
5. Garder le statut `PARTIAL_COVERAGE_WITH_ERRORS` de #117 ; aucun correctif d'extraction post hoc.

## Second verrou : capacité de réparation sur le vrai bogue
La validation statique n'est PAS une validation de correction. **Après** engagement des choix et des hashes, tenter séparément l'exécution de `tests/test_spidermiddleware_offsite.py` sous un environnement historique Python 3.8.3 avec dépendances compatibles, sans API payante. L'évaluation n'est recevable que si la version buggy **échoue** sur le test ciblé et la version fixed historique **réussit** avec les mêmes dépendances. Sans ce préalable, publier `REPRODUCER_UNCONFIRMED` et `REPAIR_INDETERMINATE`, jamais une victoire.
- En cas de reproducteur validé, chacun des patches restants serait essayé individuellement, avec **mêmes tests, limites et budget** que le bras brut (pas de changement des IDs). Compter les échecs, abstentions, succès et nombre de tests réellement exécutés. Sans assez d'information, ne pas prétendre à des budgets égaux réels.
- Les candidats de #117 peuvent ne toucher aucune ligne du défaut réel : on l'enregistre comme un résultat négatif ; ne pas adapter les règles à posteriori. Un seul cas n'infère aucune généralisation et ne prouve aucun gain d'Omega face à une règle fixe.
- L'artefact de reproduction est indépendant de celui du filtre, avec timestamps et hashes ; aucun oracle corrigé n'est ouvert pendant la sélection.
