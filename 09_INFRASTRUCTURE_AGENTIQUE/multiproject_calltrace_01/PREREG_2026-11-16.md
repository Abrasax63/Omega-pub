## Politique et budget stricts
- Source : `package/**/*.py` du commit buggy épinglé, fonctions et méthodes directes des classes au premier niveau, AST uniquement pour l'inventaire. Les fonctions imbriquées/classes imbriquées sont exclues et consignées. Les erreurs de parsing donnent `SOURCE_PARSE_ERROR`, pas victoire.
- Utiliser le **même inventaire** de fonction `(chemin,ligne,qualname,SHA source)` pour trois bras :
  - **A lexical** : pondérations figées de #119/#123 (+5 nom appelé, +3 classe mentionnée, +2 module importé, +1 jeton commun plafonné 3, +1 `download` si présent simultanément dans le module et le fichier de test). Tri `(-score, chemin, ligne, qualname)`.
  - **B présence** (contrôle) : A +1000 pour chaque fonction appelée au moins une fois pendant le(s) test(s) qui échoue(nt), sinon score A. Tri identique. Exécution du même profil que C.
  - **C récence** : A +1000 + 10×(rang de la **dernière** apparition parmi les fonctions uniques appelées dans le(s) test(s) en échec), comme #122/#123. Les appels observés dans les tests passant **sont exclus du signal**, et archivés à part comme contrôle négatif. Tri identique.
- **Une limite d'inspection commune de 10 fonctions par cas** pour A, B, C. Critère primaire pré-déclaré : `hit@10` C vs A dans les cas dont reproducer **buggy FAIL/fixed PASS** et oracle source complet. Les différences B vs C isolent l'effet de récence vs présence; `hit@5`, `best_rank`, nombre de fonctions instrumentées et coût runtime sont secondaires. Aucune modification de poids après résultats.
- **Dénominateur intangible : 3 cas sélectionnés**. Publier les trois résultats y compris les environnements défaillants, taux de reproducteurs valides et nombre admissible pour hit@10. Les cas `REPRODUCER_UNCONFIRMED`, `NO_USABLE_CALL_EVENTS`, `ORACLE_PARTIAL`, `SOURCE_PARSE_ERROR` conservent `NA`, jamais des zéros cachés ni une exclusion silencieuse. Des métriques conditionnelles sur cas valides ne prouvent pas une généralisation.
- B et C consomment des appels instrumentés, A pas : **budget d'information/calcul différent**, même budget d'INSPECTION 10. Mesurer et conserver le coût des tests (durée CPU/elapsed), les erreurs d'installation et les pertes de provenance. Les durées GitHub Actions ne mesurent PAS des tokens LLM.
- Réplicabilité : Docker Python **3.8** pour PySnooper, **3.6** pour tqdm, **3.8** pour scrapy ; noter explicitement l'écart mineur avec 3.8.1/3.6.9/3.8.3. Tests sous `--network none --read-only`, CPU=1, RAM=512MB, délai 180s/test. Pour pytest, construire les wheels pytest `6.2.5` en ligne avant sandbox, puis les installer dans un tmpfs *dans* le conteneur sans réseau. Pas d'installation réseau pendant le test.
- `pytest` installe test plugin `pytest_runtest_call` afin de profiler **uniquement le corps du test**, après collecte et imports. `unittest` construit la suite avant `sys.setprofile`; pas de comptage des appels d'import/collecte. Ne capturer que le chemin de module, premier numéro de ligne et nom de fonction ; jamais arguments/retours. 100 000 événements max par cas ; dépassement = `TRUNCATED_PROFILE`.
- **Oracle de source** (second job) : comparer les deux commits épinglés sur fichiers Python du package avec diff de lignes ; chaque hunk doit être attribuable à une unique fonction ou méthode AST de la version buggy. Insertion frontière, changement extérieur, fichier ajouté/supprimé : `ORACLE_PARTIAL`, pas de victoire certifiée. Contrôle : exécutons les mêmes tests sur fixed, et vérifions s'ils passent réellement ; idéalement profiler fixed uniquement comme contrôle négatif *après* gel.
- **Verdict cohorte** : rapport descriptif du nombre de cas éligibles et des hits A/B/C. Ne pas déclarer de gain scientifique robuste ni de supériorité générale pour N=3. Si au moins 2 cas de 2 projets distincts sont éligibles, la comparaison est exploratoire; sinon `INSUFFICIENT_REPRODUCERS`. Aucun choix adaptatif à posteriori pour obtenir une meilleure métrique.
