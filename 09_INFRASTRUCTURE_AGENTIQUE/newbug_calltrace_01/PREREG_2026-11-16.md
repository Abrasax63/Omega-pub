# OMEGA-NEWBUG-CALLTRACE-01 — préenregistrement du 16 novembre 2026

## Motivation et portée
La PR #122 a fourni un résultat local rétrospectif : une fonction du correctif historique est passée du rang 138 à 2 avec `sys.setprofile` sur `youtube-dl-1`, après reproduction officielle du bogue (#121). Cela **ne prouve pas** une capacité généralisable. La présente expérience préenregistre **un autre bogue non utilisé** pour tester si le même pilote, les mêmes poids et le même budget d'examen détectent une nouvelle fonction modifiée.

**Cas préfixé, sans examen du correctif :** BugsInPy `youtube-dl-2` (projet déjà connu, **bogue différent** de `youtube-dl-1`), corpus `soarsmu/BugsInPy@11c5f1eea954a42132cfd06bf257766a7963e0fd` ; source buggy `ytdl-org/youtube-dl@84f085d4bdb66ee025fb337bcd571eab7469da97` ; source fixed `ytdl-org/youtube-dl@9d6ac71c27b1dfb662c795ef598dbfd0286682da`. Test **fixé avant lecture du code** selon `projects/youtube-dl/bugs/2/run_test.sh` : `python -m unittest -q test.test_InfoExtractor.TestInfoExtractor.test_parse_mpd_formats`. Fichier source de test `test/test_InfoExtractor.py`. Python 3.7.0 d'après la fiche BugsInPy.

## Prévention de fuite
- Le code **buggy** et le fichier de **test** du commit fixed (et seulement ce fichier) peuvent être consultés dans le premier job pour reconstruire le checkout historique BugsInPy ; la **production fixed** et son diff ne doivent jamais y être présents.
- Le test de la version fixed est transplanté dans le checkout buggy ; même test exécuté ensuite sur la version fixed, isolément. L'engagement SHA256 des candidats A/B précède la consultation de la production fixed dans **un second job CI**.
- L'usage de ce corpus public n'exclut ni contamination pré-entraînement ni biais méthodologique : **aveuglement opérationnel**, pas aveuglement statistique garanti.

## Méthode gelée
1. Réutiliser l'instrumentation `profile_test.py` de #122 **inchangée** : importer/construire la suite avant `sys.setprofile`, observer les appels de fonctions Python du package `youtube_dl/` (chemin, `co_firstlineno`, nom, rien sur les arguments/retours). Plafond de 100 000 événements; les traces tronquées invalides, pas optimisées.
2. **Ne classer qu'après obtention d'un échec sur buggy** : un seul test ciblé, résultat `FAIL` (code non nul), une ou plusieurs fonctions du package observées et mappées ; sinon `REPRODUCER_UNCONFIRMED` ou `NO_USABLE_CALL_EVENTS`, pas de victoire.
3. A = score **lexical figé de #119 et repris #122** sur l'AST de `test/test_InfoExtractor.py`, même corpus de fonctions et méthodes directes du package `youtube_dl/`. Poids : +5 nom de fonction appelé par le test, +3 classe mentionnée, +2 module importé, +1/jeton en commun (max 3), +1 pour `download` si présent simultanément dans le nom du module et du test (condition normale, non discriminante ici). Tri `(-score, chemin, ligne, qualname)`.
4. B = **A + 1000 + 10×rang de récence du dernier appel unique mappé**, selon le même algorithme de #122 (aucune optimisation, même inventaire, tie-break). Comparaison primaire `hit@10`, secondaires `hit@5`, `hit@20`, meilleur rang. Les deux bras examinent **10 fonctions** au maximum. **B consomme plus d'information et un coût d'exécution supplémentaire**, donc aucun claim à budget calcul/information égal.
5. Sceller toutes les fonctions (chemin, lignes, nom, hash du fichier buggy, rangs A/B), le nombre d'appels (y compris non mappés), le SHA256 des traces et du test. Aucun lien à la version fixed de production.
6. Job oracle après scellement : vérifier SHA des rangs, télécharger alors seulement les commits buggy/fixed SHA exacts et transplanter le même fichier de test. Exécuter **la même** commande sur fixed dans les mêmes conditions Docker `python:3.7-slim`, réseau désactivé, CPU=1, mémoire 512 MiB, projet read-only, timeout 180s. Condition de reproduction différentielle : buggy **FAIL** et fixed **PASS**, les deux avec le test réellement exécuté. Si un import échoue, mode `REPRODUCER_UNCONFIRMED`, jamais un gain de localisation.
7. **Contrôle négatif de causalité** : pendant le job oracle exécuter le même test passing fixed avec le même profileur ; vérifier qu'une trace de fonctions peut exister sur passing et que le localisateur ne déduit pas une faute de la seule présence d'un appel. **La trace fixed ne doit jamais influencer A ou B**.
8. Oracle source : différences des fichiers `youtube_dl/**/*.py` des deux SHA par hunks ; apparier à une **unique** fonction AST de la version buggy par intervalle de lignes. Insertion à une frontière, changements hors fonctions / nouveau fichier : `ORACLE_PARTIAL` ou `ORACLE_OUT_OF_SCOPE` ; pas de `LOCAL_IMPROVEMENT` attribué sans oracle complet.
9. Interprétation : `LOCAL_IMPROVEMENT_ONE_NEW_BUG` uniquement si reproduction différentielle validée, oracle complet, B hit@10 et A non. Sinon `REGRESSION`, `NO_DIFFERENCE`, `REPRODUCER_UNCONFIRMED`, `ORACLE_PARTIAL` ou `INDETERMINATE`. **Même en cas de gain, un seul nouveau bogue ne prouve pas une supériorité générale**, ni l'exactitude d'une correction qui n'est pas générée.

## Tests non-régression
- Source buggy/test fixed strictement épinglés ; inventaire A/B identique, gel avant oracle ; rejeter SHA divergents.
- Un contrôle synthétique « fonction retourne mauvaise valeur, assertion dans test » doit enregistrer l'appel, même sans traceback du package ; profil de test passant ne doit jamais devenir un cas fautif.
- Un environnement indisponible ou un test `Ran 0 tests` invalide le gate; erreurs d'import séparées du bogue métier.
- Pas d'API payante, pas de Qwen, pas d'édition de `main`, pas de fusion, PR en brouillon. Aucun résultat positif annoncé avant les runs/artefacts vérifiés.

## Arrêt
**Ne pas changer le bogue ou les coefficients a posteriori**, même en cas d'échec. Toute amélioration ultérieure exige une nouvelle expérience et un nouvel identifiant.
