# OMEGA-EXTERNAL-REAL-01 — pré-enregistrement des corrections sur 3 projets tiers

**Date de sélection : 2026-11-15.** Branche isolée à partir de PR #103. Aucune fusion, modification de `main` ou promotion scientifique automatique.

## Question

La grammaire AST d'Omega, sans ligne fautive fournie, peut-elle proposer une réparation à **un changement de ligne** sur des *bogues réellement documentés* de projets Python indépendants, puis obtenir une reproduction correcte dans un petit banc d'exécution fondé sur les **versions historiques véritables** ? Qwen2.5-Coder-3B choisit-il mieux qu'un premier candidat déterministe à budget similaire, sur ces mêmes bogues ?

**Note d'intégrité :** les commits corrigés ont déjà été inspectés **avant le pré-enregistrement**, pour sélectionner les exemples. Le concepteur de la grammaire connaît donc les mécanismes des correctifs. Il ne faut pas appeler cela une véritable évaluation aveugle ou une preuve de transfert ouvert. Les cas ne sont néanmoins pas des bugs synthétiques inventés : sources et commits sont propres aux projets tiers.

## Mode de reproduction et limites de compatibilité

1. Cloner/fetcher chaque projet externe aux **SHA exacts** (vérifier `git rev-parse HEAD`), en conservant le SHA des fichiers sources et du dossier de tests. Ne jamais télécharger le code d'un dépôt non épinglé.
2. **Reproducteur sémantique isolé, à dépendances minimales** : extraire via AST du fichier amont la vraie fonction historique et exécuter son corps dans un conteneur Docker Python 3.11 **sans réseau**, avec des substituts standard pour quelques dépendances qui ne concernent pas directement le défaut. **Ne pas prétendre avoir fait passer les suites complètes des trois dépôts.**
3. E1 : `get_write_function(path)` écrit une chaîne dans un fichier temporaire ; vérifier que la version fautive échoue (référence au nom indéfini) et que la version corrigée écrit la valeur demandée. Deux messages réservés distincts non fournis au choix.
4. E2 : `tenumerate(range(3), start=42)` doit produire les indices 42..44 et non 0..2. Extraire la véritable fonction avec un `tqdm_class` factice de transport de l'itérable, pour isoler la sémantique de l'index `start`. Réserve : séquence de caractères `start=99`, plus cas limite vide et start=0. **Ce n'est pas un test d'intégration complet avec toutes les dépendances de tqdm.**
5. E3 : `generate_context` doit charger de l'UTF-8 même si le système choisirait par défaut `cp1252` (émulation explicite d'un système Windows non-UTF-8). Les contextes publics utilisent `éèà`, la réserve d'autres caractères non latins. **La simulation de locale ne vaut pas exécution réelle sur Windows.**
6. Pour chaque cas : la **vraie version buggy doit échouer** au moins à un test de reproduction public, la **vraie version fixed doit réussir** les mêmes tests. Sinon **`REPRODUCER_UNCONFIRMED`**, aucune prétention de réparation.
7. Proposer des modifications **sur le fichier buggy complet**, sans transmettre d'emplacement, depuis trois schémas AST généraux : substitution d'une variable non liée par une variable argument/locale plausible, correction de la distribution d'un argument entre appels imbriqués (`enumerate`), et encodage explicite pour `open()`. Pas de diff upstream fixé injecté dans le moteur. Grammaire bornée à 60 patchs par cas, **une seule ligne** changée ; les candidats se voient attribuer des IDs opaques.
8. Test faible public de chaque candidat (le même que la reproduction buggy/fixed), puis le choix Qwen si plusieurs candidats survivent. Le modèle ne reçoit ni commit corrigé, ni ligne corrigée, ni réponses réservées. Le témoin déterministe choisit le premier candidat restant dans l'ordre gelé. Le modèle doit rendre uniquement un ID autorisé, jamais un programme directement exécutable.
9. Après avoir gelé tous les choix, évaluer une réserve distincte par projet, sans s'en servir pour réordonner ou corriger les candidates. Comparer aussi à l'oracle historique corrigé sur les mêmes tests. Les temps d'exécution et le nombre de candidats sont consignés ; **aucun coût comparable aux grands algorithmes de Q^h n'est revendiqué** sur des domaines aussi différents.

## Décisions / contamination

- Le correctif historique, les tests upstream, les labels et le choix des trois dossiers sont visibles à l'expérimentateur, donc l'échantillon est **connu et non indépendant des auteurs**. Le pilote teste surtout un **nouveau raccord à des sources externes**.
- Le benchmark est petit et sélectionné ; pas d'intervalle de confiance pour l'intelligence générale, pas de certification de nouveauté algorithmique, pas de gain d'autonomie annoncé.
- Si le reproducer vérifie le bug mais le moteur ne le répare pas, noter **`REAL_BUG_REPRODUCED_BUT_NOT_REPAIRED`**.
- Si le moteur est correct sans le modèle, ne pas attribuer l'amélioration à Qwen.
- Si les projets ne peuvent être clonés ou exécutés, dire précisément quelles étapes ont réussi et ce qui reste indéterminé. Préserver les échecs.
- Aucun travail sur branches existantes des PR #98–103, aucune auto-fusion, aucune modification de `main` ni CORE.

Le **premier jalon décisif** est d'obtenir, sur GitHub Actions, le tableau buggy échoue / fixed réussit pour les trois vraies fonctions amont. **La génération neuronale ne doit pas être annoncée si ce jalon n'est pas franchi.**
