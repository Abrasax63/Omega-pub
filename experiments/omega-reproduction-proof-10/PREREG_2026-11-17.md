**Version proposée et gelée AVANT implémentation ou nouveau calcul.** Branche `experiment/omega-reproduction-proof-10-2026-11-17`, empilée sur la PR #173. Aucun changement de `main`, aucune fusion ou API LLM payante.

## Question falsifiable

Un moteur peut-il conclure qu'un **calcul numérique a été reproduit bit à bit dans un autre job GitHub Actions**, en exigeant l'identité des entrées, de la graine, du programme, de sa dépendance de calcul et de la version Python, plutôt qu'en se laissant tromper par l'égalité de la sortie ?

**Définition bornée :** `SAME-CONDITIONS-REPLAY` (SC-REPLAY) signifie seulement que deux exécutions distinctes ont les mêmes octets d'entrée, code/dépendances, seed, environnement Python consigné et octets de résultat, et que le résultat correspond à un recalcul indépendant spécifié. **Ce n'est PAS une reproduction scientifique indépendante par une équipe différente, une nouvelle découverte ou une confirmation de modèle physique**. Les jobs partagent le dépôt, l'infrastructure GitHub et un code témoin simple.

## Cinq jobs de calcul distincts (matrice GitHub, runners isolés par job)

Chaque cellule exécute le programme déterministe de type `sum(values)+échantillons pseudo-aléatoires`, avec un `receipt.json` enregistré par le processus, les bytes `inputs.json`, `computation.py` (dépendance réellement chargée), `worker_source.py` (source exécutée), `result.json` et `stdout.log`, toutes leurs empreintes SHA256 et `GITHUB_RUN_ID`/`GITHUB_RUN_ATTEMPT`/`GITHUB_SHA`, seed, version de Python, identifiant de session de processus.

- **A (référence)** : valeurs `[2,3,5,7]`, seed `4321`, code/dépendance de base.
- **B (positif)** : **mêmes** entrées, seed, dépendance, code que A dans **un autre job réel** ; SHA256 du résultat doit être identique à A et toutes les conditions exigées égales. B doit être classé `SC_REPLAY_CERTIFIED`.
- **C (contrôle négatif entrées)** : valeurs `[1,4,5,7]` de même somme, seed `4321`, même dépendance ; **même résultat attendu malgré une entrée différente** ; statut `NOT_SC_REPLAY_INPUT_DRIFT`.
- **D (contrôle négatif dépendance)** : valeurs et seed identiques à A, mais **le fichier Python `computation.py` est vraiment remplacé dans le job** par une variante algorithmique équivalente (parcours explicite au lieu de `sum`) ; sortie identique, empreinte de dépendance différente ; `NOT_SC_REPLAY_DEPENDENCY_DRIFT`.
- **E (contrôle négatif seed)** : même entrée et dépendance que A, seed `4322`, sortie pseudo-aléatoire différente ; `NOT_SC_REPLAY_SEED_DRIFT`.

Ces cinq cas sont **conçus et connus avant test** ; le pilote juge la fidélité de bout en bout et les contrôles négatifs, **pas une généralisation sur des problèmes inconnus**.

## Chaîne CI anti-fuite

1. `preflight-controls` sur push et PR : tests unitaires préenregistrés, pas de score de la cohorte évaluée.
2. `compute-evidence` en `strategy.matrix` A–E : **cinq jobs GitHub Actions distincts**, chacun avec checkout/code/runner propres. Chacun produit un ZIP via `actions/upload-artifact@v4` avec logs et reçus autoattestés. La CI prouve 5 emplois de runner, pas une indépendance scientifique extérieure.
3. `prepare-blind-dossier` : agrège les 5 artefacts, mélange en noms `packet-***` à seed fixe `60217`, conserve dans l'entrée brute uniquement un nom de paquet référence (`anchor_packet`) et les bytes de chaque paquet ; crée un `gold.json` **dans un artefact distinct**, n'incluant pas ces étiquettes dans raw.
4. `blind-inference` : lit **uniquement raw**, recoupe reçus, résultats, logs et SHA et **recalcule de manière indépendante** la sortie attendue à partir de l'entrée et de la seed. Applique les critères SC-REPLAY : un résultat identique seul ne suffit pas. Émet les diagnostics et abstentions sans accès au gold.
5. `independent-scoring` : autre job isolé lit raw/prédictions/gold ; recalcule par une autre implémentation les SHA, les cinq chemins de job et les cinq labels préenregistrés. Zéro fausse certification, zéro faux rejet de B. Conserve les résultats négatifs, empreintes et liens GitHub.

**Limite de confidentialité :** les artefacts de gold dans un dépôt public sont accessibles via GitHub. La séparation est effective entre jobs, **non cryptographique contre un agent muni d'un navigateur ou d'un accès GitHub externe**.

## Métriques et conditions de succès

- **5 cellules GitHub distinctes** effectivement exécutées ; chaque cellule a un `session_uuid` différent et génère une trace source et le même `run_id` (car même workflow) ; le scorer vérifiera les dénominateurs.
- Cinq dossiers correctement validés bit à bit; 1 positif B/1, 3 négatifs C-D-E/3, référence A neutre; **0 faux positif de reproduction**, **0 faux certificat scientifique**.
- Contrôles adversariaux : fichier de résultat altéré mais JSON valide, logs divergents, sortie identique avec entrée différente, dépendance différente, seed différente, absence de `receipt`, incohérence de version Python, `session_uuid` dupliqué, dossier gold injecté dans raw, copie de même ZIP au lieu d'exécution distincte.
- L'inférence est autorisée à renvoyer `ABSTAIN` sur données manquantes mais une absence de B certifié n'est **pas** un succès.
- Label `SC_REPLAY_PIPELINE_VERIFIED` uniquement si l'ensemble des exigences passe. Le nombre de reproductions **scientifiquement indépendantes** reste `INDÉTERMINÉ`.
- Les prix CPU, tarifs Python/GitHub et limitations environnementales sont distincts des coûts d'API LLM.

## Aucun raccourci scientifique

Cette expérience n'établit ni indépendance des équipes, ni causalité scientifique, ni équivalence du calcul dans des environnements hétérogènes, ni reconstruction de sources inconnues. Des versions Python identiques dans cinq jobs du même workflow ne forment pas un échantillon indépendant des configurations. Si GitHub Actions est bloqué par quota/infra, consigner `CI_INCOMPLETE`, ne pas inventer de score ni contourner par un changement de cohorte après consultation.
