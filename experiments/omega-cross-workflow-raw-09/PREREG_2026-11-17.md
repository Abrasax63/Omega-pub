## Question

Le pilote #171 fabriquait des traces de *sous-processus* dans un seul job. Ici, **récupérer et examiner de vrais journaux de jobs GitHub Actions** et de **vraies archives ZIP d'artefacts** produits **par plusieurs workflows GitHub distincts**, puis grouper les archives par `run_id` **uniquement lorsqu'un lien d'artefact explicite figure dans le contenu brut d'un log GitHub**. Reconnaître deux artefacts de la même exécution et deux exécutions distinctes du même commit ; ne PAS inférer la provenance par simple égalité de nom ou de SHA de fichiers. Conserver les abstentions pour les archives non liées.

Attention : les liens affichés dans un log d'upload sont des indications du fournisseur et non des **preuves d'indépendance scientifique**. Cette évaluation juge la reconstruction de **liens de provenance d'invocations GitHub**, non l'autonomie mathématique, ni la véracité des résultats contenus dans les ZIP. Même des workflows distincts sur le même SHA ne prouvent pas la réplication indépendante.

## Collecte authentique via API GitHub dans GitHub Actions

Un workflow isolé sur PR (pas sur push) télécharge dans un **job producteur** les réponses REST de `/actions/runs/{id}`, `/actions/runs/{id}/jobs`, `/actions/runs/{id}/artifacts`, `/actions/jobs/{jobid}/logs` (octets texte), et `/actions/artifacts/{artifact_id}/zip` (véritables bytes ZIP) à l'aide de `GITHUB_TOKEN` limité à `actions:read, contents:read`. Journaliser taille et SHA256, refuser les réponses HTML, archives corrompues ou dépassant le plafond. Aucun secret ou jeton stocké dans l'archive.

**Séparation physique des jeux de données :**
- `raw` : sept paquets ZIP réels avec noms opaques; chacun porte uniquement un **`artifact_id` comme numéro de transport**, sans `run_id`, et un jeu de logs bruts `trace-NNN.log`, sans étiquette de run. Les logs sont ceux de tous les jobs de ces cinq runs, sans leur `job_id` dans le nom visible. Un inventaire liste les seuls fichiers et SHA256 de transport, sans gold. Les paquets sont mélangés par une seed figée `59221`, sans calibration sur leur contenu.
- `gold` : **séparé** : exact `artifact_id→run_id/run_attempt/head_sha` depuis l'API publique de GitHub et associations `job_id→run_id`; inclut les éventuelles pièces omises ou incompréhensibles. Le gold ne sera **pas téléchargé** dans le job d'inférence.
- `predictions` : sortie figée du parseur seulement sur `raw`.
- `score` : job séparé lit raw/predictions/gold et vérifie indépendamment les regroupements sur la vérité REST.

Deux manipulations déclarées :
1. **Miroir simulé au niveau *transport*** : créer une copie binaire du premier ZIP et conserver son **même artifact_id** dans une seconde enveloppe (aucun nouveau ZIP GitHub réellement créé). Le parseur doit le dédupliquer sans créer une nouvelle exécution.
2. **Archive orpheline au niveau *transport*** : copier binaire le deuxième ZIP, mais **omettre l'artifact_id**. Bien qu'un contenu identique apparaisse ailleurs, le parseur doit **s'abstenir** de lui attribuer un run sans lien d'upload. Ce contrôle est injecté, non une découverte de provenance réelle dans les sources.

Ainsi **9 paquets** attendus : 7 archives originelles, 1 miroir de transport, 1 orphelin. Les identifiants de paquet opaques ne sont pas ordonnés par origine.

## Stratégie de décision gelée (pas de LLM)

Analyser les **lignes des journaux bruts** pour l'URL imprimée par GitHub Actions lors de `actions/upload-artifact`, de forme `.../actions/runs/<run_id>/artifacts/<artifact_id>`; les modules d'actions peuvent aussi imprimer `Artifact ID is <artifact_id>`, mais **un ID isolé sans run ID dans le même contexte explicite ne permet pas de certifier le groupe**. Conserver les liens positifs seulement lorsqu'un couple `(run_id, artifact_id)` figure ensemble dans une URL de téléchargement explicite issue d'un log. **Ne pas** lire le gold, n'utiliser ni l'égalité de ZIP ni le nom `artifact` pour deviner les liens manquants.

Pour un ZIP associé par URL à un run, le niveau certifié est `PROVIDER_LOG_LINK` seulement. Le `run_attempt` de l'API et le `head_sha` **ne sont pas déduits** si absents du contenu brut ; le score peut certifier le regroupement par `run_id`, mais l'autonomie scientifique reste `INDETERMINATE`. Archive sans lien explicite : `ABSTAIN`, sans dédupliquer par contenu. URL conflictuelle pour le même artifact_id : `CONFLICT`, pas un choix arbitraire.

## Références et métriques, pas d'optimisation post-hoc

Comparateur faible `NAME_ONLY` : regrouper les archives de même nom d'artefact (une donnée de transport), sans accéder aux logs. Il n'est **pas un système de vérité** et ses scores sont jugés avec le même gold.
Comparateur conservateur `ABSTAIN_ALL` : zéro fausse origine, mais zéro rappel. Le moteur visé doit être évalué sur précision des liens attribués, rappel sur les **7 ZIP vrais** dont le log donne un lien, abstentions injustifiées, comportement du miroir/orphelin, et zéro fausse certification scientifique. Le cas de log manquant doit rester abstention même quand un ZIP est non ambigu par son contenu.

**Conditions de succès préenregistrées** : toutes les archives de provenance demandées sont téléchargées, **tous les logs** des jobs des cinq runs sont collectés et préservés ; aucune erreur de regroupement parmi les liens certifiés ; miroir et orphelin corrects ; aucune prétention d'indépendance scientifique ; plus de liens correctement certifiés que `ABSTAIN_ALL` si et seulement si des URLs explicites sont présentes. Si aucune URL explicite ne figure, statut `NO_PROVIDER_URL_SIGNAL` et score de rappel nul, sans changer la règle ; si la collecte échoue, `COLLECTION_BLOCKED`.

**Tests avant ouverture des sources** : 14 tests unitaires avec journaux **synthétiques et distincts des cinq runs** (URLs factices), vérification du parseur, injection de faux liens ou SHA, absence de `artifact_id`, doublon d'archive, téléchargement ZIP invalide, dépassement budget, refus de clés API/secrets, impossibilité de lire le gold. CI `push` : 14 tests seulement, aucune collecte des 5 runs. CI `pull_request` : collecte **une seule cohorte gelée**, archivage raw et gold séparément, inférence aveugle, notation auditée. Conserver toute issue négative, ne pas modifier les règles après lecture.

## Limites préannoncées

- Les logs et ZIP sont authentiques **si et seulement si les octets proviennent des endpoints GitHub attendus** sous token de lecture ; pas d'attestation indépendante des snapshots.
- Le gold est en artefact publiquement consultable à terme : sa séparation est **inter-job**, non une confidentialité adversariale contre un modèle muni d'un navigateur extérieur.
- Le fichier ZIP ne contient pas normalement son propre ID d'artefact GitHub, que GitHub attribue après upload. Nous donnons donc au parseur un **ID de transport** du fournisseur, mais **pas** la correspondance `run_id`, et il doit la retrouver dans les logs. Ce n'est pas une attribution depuis les octets ZIP seuls.
- L'égalité de ZIP, du SHA de commit ou du résultat mathématique n'est pas un certificat d'indépendance ou de duplication d'une exécution.
- Pas de données externes à ce dépôt ni d'entraînement LLM ; l'absence de dérive entre données sources n'est pas une preuve mathématique.

Prochaine vérification réellement distincte : logs **inconnus** de projets externes et procédures d'exécution attéstées indépendamment, avec gold séparé et scorer aveugle.
