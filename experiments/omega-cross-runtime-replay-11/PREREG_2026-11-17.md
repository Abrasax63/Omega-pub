# OMEGA-CROSS-RUNTIME-REPLAY-11 — protocole préenregistré du 17 novembre 2026

**Enregistré avant tout code et avant toute mesure de ce pilote.** Branche `experiment/omega-cross-runtime-replay-11-2026-11-17` empilée sur PR #176 ; `main`, CORE et les PR précédentes inchangés, aucun appel de modèle ou API payante.

## Nouvelle frontière expérimentale

La PR #176 certifie un calcul rejoué dans **deux jobs du même workflow** sous le même Python. Ce pilote déclenche **DEUX WORKFLOWS GitHub Actions distincts**, chacun donnant un `run_id` propre, sur le même commit de la branche expérimentale, avec **Python 3.11 pour workflow SOURCE-A** et **Python 3.12 pour workflow SOURCE-B**. Les données/versions sont lues réellement depuis les jobs. Un troisième workflow d'évaluation est une PR DRAFT avec deux étapes aveugle et scoring isolées.

Une exécution n'est pas une validation scientifique indépendante du même théorème : `scientific_independence=INDETERMINATE` restera strictement vrai. Les deux workflows partagent le dépôt, l'auteur, les hypothèses, le runner GitHub Ubuntu et le programme.

## Définition vérifiable, plus étroite qu'une affirmation scientifique

`CROSS_RUNTIME_REPLAY_VERIFIED` signifie : deux runs et workflows GitHub distincts (IDs vérifiés par l'API REST du dépôt) ont exécuté **le même code calculatoire et dépendance en octets, les mêmes valeurs d'entrée, la même graine**, avec **versions de Python réellement différentes et déclarées**, et produit **la même sortie bit-à-bit**, que l'on peut recalculer **par un vérificateur indépendant n'exécutant pas le module testé**. L'écart de version est accepté **uniquement** pour les 3.11 et 3.12 du protocole ; ce statut ne signifie pas identité d'environnement ni compatibilité universelle.

Les reçus journalisent `GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`, `GITHUB_WORKFLOW`, `GITHUB_SHA`, version Python de l'interpréteur, `session_uuid`, SHA256 du fichier d'entrée et du programme chargé, dépendance, résultat. Les journaux des vrais jobs contiennent begin/end et les empreintes correspondantes.

## Cohorte gelée

- **A** : source de référence sous workflow A / Python 3.11 : `values=[2,3,5,7]`, `seed=4321`, dépendance `algorithms.py`.
- **B** : workflow B / Python 3.12 : mêmes données, seed et fichier de dépendance/programme que A : résultat identique, statut `CROSS_RUNTIME_REPLAY_VERIFIED`.
- **C** : workflow B / Python 3.12 : `values=[1,4,5,7]`, même somme et seed, sortie bit-identique à A malgré l'entrée différente ; `NOT_REPLAY_INPUT_DRIFT`.
- **D** : workflow B / Python 3.12 : mêmes données et seed que A, mais exécute réellement une **autre implémentation du module de dépendance** donnant les mêmes sorties ; `NOT_REPLAY_DEPENDENCY_DRIFT`.
- **E** : workflow B / Python 3.12 : mêmes valeurs/dépendance, seed `4322`, sortie différente ; `NOT_REPLAY_SEED_DRIFT`.

Le résultat contient une somme et huit blocs de SHA256 pseudo-aléatoires déterministes `sha256(seed || index)`, afin que la production soit explicitement reproductible entre versions de Python sans dépendre de changements possibles de `random.randrange`. Tous les cas sont connus avant exécution. L'égalité d'une seule somme, du SHA de sortie, ou d'un commit ne suffit jamais pour certifier le rejouage.

## Anti-fuite et CI

1. Le workflow `preflight` vérifie les algorithmes sur fixtures temporaires et cas adversariaux (tests unitaires) sans accès au corrigé du run évalué.
2. Les workflows `source-a` et `source-b` sont déclenchés **sur push de branche**, chaque workflow ayant son nom et son propre GitHub `run_id`. SOURCE-A produit A, SOURCE-B produit B,C,D,E par quatre jobs dans son run. Pas de déclenchement `main`.
3. À l'ouverture de la PR DRAFT, `cross-run-auditor` interroge l'API GitHub pour sélectionner les **deux runs source `push` en statut SUCCESS sur exactement le commit HEAD de la PR**. L'ID d'un autre commit, d'un autre workflow ou d'un run rouge entraîne `SOURCE_RUNS_UNAVAILABLE`, pas de faux scoring.
4. `collect` télécharge les **5 artefacts binaires réels** depuis leurs deux runs via `actions/download-artifact@v4` en `actions:read`, sans API payante. Le dossier brut est anonymisé sous les alias `packet-000...`, mais conserve le `run_id/workflow` des reçus et un `anchor_packet` A. Le gold (`A/B/C/D/E` et verdicts attendus) est archivé **séparément**.
5. `blind-inference` télécharge uniquement le dossier brut, rejoue une formule mathématique indépendante, vérifie hashes, code, entrée, logs, sessions et provenance multi-run, puis publie les décisions avant de voir le gold. Tous les cas incomplets donnent abstention/échec fermé.
6. `independent-scoring` télécharge raw+prédictions+gold, reconstruit le résultat et vérifie deux workflows/runs et versions Python différentes, zéro faux certificat sur C,D,E.

**Limite de confidentialité :** le gold GitHub reste potentiellement accessible aux lecteurs du dépôt. La séparation est opérationnelle **entre jobs**, pas garantie contre un modèle qui naviguerait hors de l'artefact.

## Critère préenregistré et adversaires

Succès `CROSS_RUNTIME_REPLAY_PIPELINE_VERIFIED` uniquement si : A et B de deux **run IDs ET workflow names différents**, même SHA de commit, python 3.11 vs 3.12, 5 sessions distinctes, 1 positif B/1, 3 négatifs C,D,E/3, 0 faux positif, 0 faux verdict scientifique, 5 recalculs indépendants réussis. Tests sur résultat trafiqué, version Python trompeuse, input mismatch sortie identique, dépendance différente sortie identique, seed changée, même run IDs, même workflow, duplication de session, absence de logs/reçus, gold accidentel dans raw. Les tarifs CPU ne sont pas mis au même budget que les heuristiques précédentes.

Si le token GitHub `actions:read`, les artefacts ou les quotas externes empêchent la collecte, statut `INFRASTRUCTURE_BLOCKED`, sans remplacer les vrais runs par des fixtures. Si une variante positive n'est pas certifiée, échec réel du pilote. Pas de modification du gold après lecture des résultats, pas de promotion scientifique automatique.

**Prochaine falsification après succès éventuel :** calcul scientifique externe sans source commune et modèles de données plus riches ; évaluation de reproductibilité à tolérance numérique, non seulement octet pour octet, et contrôle des hypothèses théoriques.
